The automated pipeline is the **only** way to run control extraction, issue
synthesis, classification, chart generation, risk discovery, risk scoring,
risk tagging, and risk owner assignment — the equivalent per-stage manual
endpoints have been removed.
Clients call **one ingest endpoint** to begin processing and **one status
endpoint** to track progress. All intermediate stages run as Celery tasks
behind RabbitMQ, with Redis as the result backend.

Process narrative: [Automated Ingest Pipeline](/flow/00-automated-ingest-pipeline).

<Warning>
These two endpoints use a **different authentication mechanism** from the rest
of the API — see [Authentication](#authentication) below.
</Warning>

---

## Authentication

`POST /ingest/{clientOrgId}` and `GET /pipeline/status/{clientOrgId}` are
authenticated against an **external backend**, not ISO Robot's own JWT.

| Header | Value |
| --- | --- |
| `Authorization` | `Bearer <existing-backend token>` |
| `X-User-Id` | the calling user's id |
| `X-User-Email` | the calling user's email |
| `X-Org-Id` | the organisation id — must equal `{clientOrgId}` in the path |

ISO Robot verifies the token against `VERIFY_API_URL` (with a 30-minute sliding
cache) before doing any work. See the backend README's "External-backend auth"
section for the full contract.

## Ingest documents

```http
POST /ingest/{clientOrgId}
```

**Auth:** external-backend verify · **Response:** `202 Accepted`

Accepts one or more **PDF** files, registers each by content hash (SHA-256)
scoped to the organisation, creates a `pipeline_runs` row, and enqueues the
batched Celery pipeline. Returns immediately with a `pipeline_run_id` —
processing happens asynchronously. Uploads are streamed to disk while hashing
(constant memory per file), so large batches don't load every file into RAM.

If the org already has an active run, this upload is accepted as a **`waiting`**
run that auto-starts (FIFO per org) when the active one finishes — up to
`PIPELINE_MAX_QUEUED_RUNS` (default 10). Set that to `0` to instead reject
concurrent uploads with `409 PIPELINE_RUN_IN_PROGRESS`.

### Path parameters

| Param | Description |
| --- | --- |
| `clientOrgId` | Target organisation UUID |

### Request (multipart form)

| Field | Type | Required | Default | Description |
| --- | --- | --- | --- | --- |
| `file` | file | Yes | — | PDF document to ingest. Repeat the field for multiple files. Non-PDF or empty files are rejected per-file (`"status": "rejected"`), not for the whole request. |
| `save_to_storage` | boolean | No | `PIPELINE_SAVE_TO_STORAGE_DEFAULT` (`false`) | When `true`, persist files permanently under the org's document folder. When `false`, files live in a per-run temp directory and are deleted once the run completes. |
| `force_reprocess` | boolean | No | `false` | Re-run the pipeline even when this sha256 was already registered for this org. |

### Example (curl)

```bash
curl -X POST "http://157.20.190.175:8000/api/v1/ingest/{clientOrgId}" \
  -H "Authorization: Bearer $EXISTING_BACKEND_TOKEN" \
  -H "X-User-Id: $USER_ID" \
  -H "X-User-Email: user@example.com" \
  -H "X-Org-Id: {clientOrgId}" \
  -F "file=@policy.pdf" \
  -F "file=@controls.pdf" \
  -F "save_to_storage=false"
```

### Response `202`


`documents[].status` is one of:

| Value | Meaning |
| --- | --- |
| `queued` | New content (unseen sha256 for this org); queued for the full pipeline |
| `reprocessed` | Previously-seen content, re-queued because `force_reprocess=true` |
| `duplicate` | Previously-seen content, skipped (`force_reprocess` omitted/`false`) |
| `rejected` | Not a PDF, or the upload was empty |

### Errors

| HTTP | code | Meaning |
| --- | --- | --- |
| 400 | `FILE_UPLOAD_FAILED` | No files supplied |
| 401 | `UNAUTHORIZED` | Missing token or `X-User-Id`/`X-User-Email`/`X-Org-Id` headers |
| 401 | `SESSION_INVALID` | External verification failed |
| 403 | `FORBIDDEN` | `X-Org-Id` does not match `clientOrgId`, or identity mismatch |
| 404 | `CLIENT_ORG_NOT_FOUND` | Unknown organisation |
| 409 | `PIPELINE_RUN_IN_PROGRESS` | Only when `PIPELINE_MAX_QUEUED_RUNS=0` (queuing disabled) and a run is already active. Otherwise the upload is queued as a `waiting` run instead. |
| 429 | `PIPELINE_QUEUE_FULL` | The org already has `PIPELINE_MAX_QUEUED_RUNS` waiting runs — try again once some complete |
| 503 | `EXTERNAL_AUTH_UNAVAILABLE` | The verify backend is unreachable (fails closed) |

<Warning>
Ensure the risk library is seeded (`POST /risk-library/seed-from-poc`) before
ingesting. The automated pipeline runs risk discovery against that catalogue.
</Warning>

## Get pipeline status

```http
GET /pipeline/status/{clientOrgId}
```

**Auth:** external-backend verify · **Response:** `200`

Returns the current state of the organisation's pipeline — the **latest run**
by default. Use this endpoint to poll progress after ingest.

### Path parameters

| Param | Description |
| --- | --- |
| `clientOrgId` | Organisation UUID |

### Query parameters

| Param | Type | Description |
| --- | --- | --- |
| `pipeline_run_id` | uuid | Return a specific run instead of the latest |

### Example (curl)

```bash
curl "http://157.20.190.175:8000/api/v1/pipeline/status/{clientOrgId}" \
  -H "Authorization: Bearer $EXISTING_BACKEND_TOKEN" \
  -H "X-User-Id: $USER_ID" \
  -H "X-User-Email: user@example.com" \
  -H "X-Org-Id: {clientOrgId}"
```

`steps[]` rows track progress at batch granularity. Batched stages
(`extract_controls`, `issues_from_controls`, `classify_issues`, `score_risks`)
emit one row per batch — each carries a `batch_index` and the ids it processed —
plus a run-level summary row (`batch_index: null`) written when the stage
finishes. Single-shot org-wide stages (`generate_charts`, `risk_discovery`,
`risk_tagging`, `risk_owner_assignment`) emit just the summary row.

`stage_summary[]` rolls up `steps[]` by stage (batch/document counts, failed
counts, and earliest/latest timestamps). Use it for compact progress UIs; use
`steps[]` for per-batch detail.

The response also carries `stage_totals` — per-stage batch counters
(`{stage: {total_batches, completed_batches, failed_batches}}`) that feed the
intra-stage portion of `progress_percent`.

The response does **not** include elapsed-time or ETA fields — poll `status`,
`current_stage`, and `steps[].status` instead.

### `status` values (pipeline run)

| Value | Meaning |
| --- | --- |
| `waiting` | Accepted while another run was active; auto-starts (FIFO per org) once that run finishes |
| `queued` | Run dispatched, waiting for a worker to pick it up |
| `running` | At least one stage is actively processing |
| `completed` | The pipeline finished for every queued document. Check `failed_documents`/`stage_summary` — a single document or batch failure does **not** fail the whole run. |
| `failed` | A **critical** stage (extraction or issue generation) had all of its batches fail, so nothing downstream could run (see `error`) |

### `current_stage` values

| Stage | Description |
| --- | --- |
| `ingest_register` | Documents hashed, deduplicated, registered |
| `extract_controls` | Azure DI + LLM control extraction (one batch task per document, run in parallel) |
| `issues_from_controls` | Issue synthesis from this run's new controls (incremental; batched) |
| `classify_issues` | PESTEL / SWOT / TVRA classification of this run's new issues |
| `generate_charts` | Chart aggregation (`aggregate_classifications`) |
| `risk_discovery` | BM25 + LLM matching to the risk library |
| `score_risks` | Inherent/residual risk scoring, plus auto-promotion to `risks` rows |
| `risk_tagging` | Catalog + LLM tag recommendations (auto-applied above the confidence threshold) |
| `risk_owner_assignment` | Hierarchy-based owner recommendations, auto-applied to `risks.owner_user_id` above the confidence threshold |
| `complete` | Pipeline finished |

### Errors

| HTTP | code | Meaning |
| --- | --- | --- |
| 401 | `UNAUTHORIZED` / `SESSION_INVALID` | Missing or invalid token/headers |
| 403 | `FORBIDDEN` | `X-Org-Id` does not match `clientOrgId` |
| 404 | `CLIENT_ORG_NOT_FOUND` | Unknown organisation |
| 404 | `PIPELINE_RUN_NOT_FOUND` | No run exists for the org yet, or `pipeline_run_id` doesn't belong to it |

## Cancel active pipeline run

```http
POST /pipeline/cancel/{clientOrgId}
```

**Auth:** external-backend verify · **Response:** `200`

Marks the organisation's active (`queued` or `running`) pipeline run as `failed`
with error `"Cancelled by user"`, cleans up ephemeral upload temp files when
applicable, and releases the active-run slot. If the org has a `waiting` run
queued behind it, that run auto-starts next.

Use this when a run is stuck or you need to retry without waiting for Celery to finish.

### Example (curl)

```bash
curl -X POST "http://localhost:8000/api/v1/pipeline/cancel/{clientOrgId}" \
  -H "Authorization: Bearer $EXISTING_BACKEND_TOKEN" \
  -H "X-User-Id: $USER_ID" \
  -H "X-User-Email: user@example.com" \
  -H "X-Org-Id: {clientOrgId}"
```

### Response `200`

```json
{
  "status": "success",
  "message": "Pipeline run cancelled",
  "data": {
    "client_org_id": "...",
    "pipeline_run_id": "...",
    "status": "failed",
    "error": "Cancelled by user"
  }
}
```

### Errors

| HTTP | code | Meaning |
| --- | --- | --- |
| 401 | `UNAUTHORIZED` / `SESSION_INVALID` | Missing or invalid token/headers |
| 403 | `FORBIDDEN` | `X-Org-Id` does not match `clientOrgId` |
| 404 | `CLIENT_ORG_NOT_FOUND` | Unknown organisation |
| 404 | `NO_ACTIVE_PIPELINE_RUN` | No `queued`/`running` run for this org |

<Note>
In Docker Compose, ephemeral uploads (`save_to_storage=false`) are stored under
`PIPELINE_INGEST_TEMP_DIR` (`/app/backend/data/ingest-tmp`), shared across the
API and Celery worker containers via the `backend/data` volume. Without this,
workers cannot read files the API saved to container-local `/tmp`.
</Note>

## Polling guidance

<Steps>
  <Step title="Capture pipeline_run_id">
    From the `202` ingest response — optional for polling (status defaults to
    the latest run for the org).
  </Step>
  <Step title="Poll every 3–10 seconds">
    `GET /pipeline/status/{clientOrgId}` while `status` is `queued` or `running`.
  </Step>
  <Step title="Stop when terminal">
    Exit the poll loop when `status` is `completed` or `failed`.
  </Step>
  <Step title="Fetch output">
    Read controls, issues, classifications, candidates, assessments, tags, and
    risks via the existing list endpoints.
  </Step>
</Steps>

<Tip>
`progress_percent` is a coarse UI hint (`current_stage`'s index in the 10-stage
list). Prefer `current_stage`, `stage_summary[]`, and `steps[].status` for
integration logic. There is no server-side ETA — keep polling until `status` is
`completed` or `failed`.
</Tip>

## Relationship to the (removed) legacy job endpoints

The automated pipeline runs the same domain logic as the old manual triggers,
but chains it internally — the endpoints themselves are **gone**:

| Pipeline stage | Removed manual endpoint |
| --- | --- |
| Extract controls | ~~`POST /control-documents/extract/{orgId}`~~ |
| Issues from controls | ~~`POST /issues/from-controls/{orgId}`~~ |
| Classify issues | ~~`POST /issues/classify`~~ |
| Risk discovery | ~~`POST /risk-discovery/run`~~ |
| Risk scoring | ~~`POST /risk-scoring/run`~~ |
| Risk tagging | ~~`POST /risk-tagging/run`~~ |
| Risk owner assignment | ~~`POST /risk-assignments/run`~~ |

Two global (non-org-scoped) legacy endpoints remain for low-level debugging:
`POST /controls/extract` and the generic `POST /jobs`. See
[Jobs](/api-reference/jobs) for their poll pattern (`GET /jobs/{jobId}`).
